# 02_11 — A2A 协议详解

> Agent-to-Agent Protocol — Google 提出的 Agent 间通信标准。和 MCP 互补，MCP 管 Agent↔工具，A2A 管 Agent↔Agent。

---

## 一、MCP 不解决的问题

MCP 解决的是 **Agent 怎么调用外部工具**。但真实场景中：

```
用户: "帮我实现用户认证系统"

这不是一个 Agent 能搞定的:
  ├─ Agent A: 设计数据库 schema
  ├─ Agent B: 写后端 API
  ├─ Agent C: 写前端组件
  └─ Agent D: 写集成测试

A、B、C 需要互相通信:
  - A 把 schema 告诉 B
  - B 把 API 接口告诉 C
  - D 需要知道 A+B+C 的产出
```

MCP 管不了 Agent 之间的通信 → 这就是 A2A 要解决的问题。

---

## 二、A2A 核心概念

### 2.1 三大角色

```
┌──────────────┐         ┌──────────────┐
│  Client      │ ←──→   │  Remote      │
│  Agent       │  A2A    │  Agent       │
│ (发起通信)   │         │ (接收请求)   │
└──────────────┘         └──────────────┘

A2A 同时支持:
  - HTTP (请求-响应)
  - SSE (流式推送，长任务进度通知)
  - gRPC (高性能内部通信)
```

### 2.2 四大原语

| 原语 | 说明 | 示例 |
|------|------|------|
| **Task** | 一个可追踪的工作单元 | "创建数据库 migration" |
| **Message** | Agent 间的对话消息 | "schema 有 3 张表: users, sessions, logs" |
| **Artifact** | Task 产出的文件/内容 | migration.sql 文件 |
| **Skill** | Agent 声明自己能做什么 | "我能处理数据库 schema 变更" |

### 2.3 Agent Card

每个 Agent 公开一张 "名片"，声明自己的能力：

```json
{
  "name": "Backend Dev Agent",
  "description": "后端开发专家，擅长 Node.js/PostgreSQL",
  "url": "http://agent-b.internal:8080",
  "skills": [
    {
      "name": "design_api",
      "description": "设计 RESTful API 接口"
    },
    {
      "name": "write_migration",
      "description": "编写数据库 migration"
    }
  ],
  "capabilities": {
    "streaming": true,      // 支持流式响应
    "artifacts": true       // 支持产出文件
  }
}
```

## 三、A2A 通信流程

### 完整示例：两个 Agent 协作建表

```
Agent Coordinator (编排者)
  │
  │ 1. 发送 Task
  ▼
Backend Agent (工作者)
  │
  │ 2. 返回 Message: "需要知道用户模型有哪些字段"
  ▼
Agent Coordinator
  │
  │ 3. 去问 User Agent → 拿到字段列表 → 转发
  ▼
Backend Agent
  │
  │ 4. 产出 Artifact: migration.sql
  │ 5. 更新 Task 状态: completed
  ▼
Agent Coordinator → 把 migration.sql 交给下一个 Agent
```

### HTTP API 示例

```http
# 1. Client Agent 向 Remote Agent 发送 Task
POST http://backend-agent:8080/a2a/tasks
Content-Type: application/json

{
  "type": "task",
  "task": {
    "id": "task-001",
    "description": "创建 users 表的 migration 文件",
    "context": {
      "fields": ["id: UUID", "email: string", "name: string"],
      "framework": "PostgreSQL + Knex.js"
    }
  }
}

# 2. Remote Agent 响应（流式 SSE）
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: message
data: {"type": "message", "content": "正在分析字段类型..."}

event: message
data: {"type": "message", "content": "创建 migration..."}

event: artifact
data: {"type": "artifact", "name": "migration.sql", "url": "http://backend-agent:8080/artifacts/task-001/migration.sql"}

event: task_complete
data: {"type": "task_status", "status": "completed"}
```

## 四、A2A vs MCP

| | MCP | A2A |
|---|---|---|
| **提出者** | Anthropic | Google |
| **解决什么** | Agent ↔ 工具/数据源 | Agent ↔ Agent |
| **通信方向** | Agent 调工具 (单向) | Agent 之间 (双向) |
| **核心概念** | Tools / Resources / Prompts | Tasks / Messages / Artifacts / Skills |
| **传输** | stdio / SSE / Streamable HTTP | HTTP / SSE / gRPC |
| **谁用** | Claude Code, Cursor, Cline | 待生态发展 |
| **成熟度** | 2025.03 发布，快速增长 | 2025.05 发布，早期 |

### 互补关系

```
┌──────────────────────────────────────┐
│           多 Agent 系统               │
│                                      │
│  Agent A ←──→ Agent B   (A2A 通信)   │
│     │            │                   │
│     └─────┬──────┘                   │
│           │                          │
│     MCP 调工具                       │
│           │                          │
│     ┌─────┴──────┐                   │
│     │ 工具服务器  │                   │
│     └────────────┘                   │
└──────────────────────────────────────┘
```

## 五、A2A 的现状与展望

### 当前状态 (2026.06)

- **Google 主推**，但生态远不如 MCP 成熟
- **Google Agent Development Kit (ADK)** 内置 A2A 支持
- **社区 Stage**: 早期，主要参与者是 Google 生态企业

### 未来趋势

```
短期 (2026):
  ─ MCP 继续主导 Agent↔工具通信
  ─ A2A 在 Google 生态内推广

中期 (2027):
  ─ MCP + A2A 互补格局确立
  ─ 工具层用 MCP，协作层用 A2A

长期:
  ─ 协议趋于统一或融合
  ─ Agent 间通信像今天的 REST API 一样普遍
```

## 六、和本项目的关联

Claude Code 目前使用 **AgentTool** 实现多 Agent（Spawn 子进程 + Worktree 隔离），走的是一种"进程内子 Agent"模式，不是 A2A 的网络通信模式。

A2A 更适合的场景：
- 跨机器/跨服务的 Agent 协作
- 长任务（持续数小时甚至数天）
- 异构 Agent 系统（不同的 Agent 用不同的技术栈）

如果未来你想做多 Agent 协作的产品（如 AI 开发团队），A2A 是比进程 Spawn 更标准的方案。
