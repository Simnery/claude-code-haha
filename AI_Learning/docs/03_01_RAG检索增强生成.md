## 一、什么是 RAG？

### 一句话定义

> RAG（Retrieval-Augmented Generation）= 先从知识库**检索**相关信息，再让模型基于检索结果**生成**回答。

### 为什么需要 RAG？

模型的训练数据有时间截止日期，且不知道你的私有文档。RAG 解决两个问题：

| 问题 | 不用 RAG | 用 RAG |
|------|---------|--------|
| 知识过时 | 模型不知道2026年的新API | 检索最新文档后回答 |
| 私有知识 | 模型不知道公司内部代码规范 | 检索内部文档后回答 |
| 幻觉 | 模型可能编造不存在的事实 | 基于真实文档回答 |

### 工作流程

```
用户提问: "这个项目的 CI/CD 怎么配置的？"
  ↓
1. 把问题转成向量 (Embedding)
  ↓
2. 在知识库中搜索最相似的文档 (Retrieval)
  ↓
3. 把相关文档 + 原问题一起发给模型 (Augmented)
  ↓
4. 模型基于文档生成回答 (Generation)

"根据 docs/ci-cd.md，项目使用 GitHub Actions，
  配置文件在 .github/workflows/ 下..."
```

## 二、RAG 四大步骤

### Step 1: 文档切分 (Chunking)

把长文档切成小段，每段是一个"检索单元"。

#### 切分策略

| 策略 | 说明 | 适用 |
|------|------|------|
| **固定大小** | 每 500 字切一段，重叠 50 字 | 通用，最简单 |
| **按段落** | 按自然段落切分 | 结构清晰的文档 |
| **语义切分** | 用模型判断语义边界 | 高质量要求 |
| **按标题** | 按 Markdown 标题层级 | 技术文档最佳 |

```python
# 固定大小切分示例 (LangChain)
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # 每段最多 500 字符
    chunk_overlap=50,      # 相邻段重叠 50 字符（保留上下文）
    separators=["\n\n", "\n", "。", ".", " "]  # 优先在这些位置切
)
chunks = splitter.split_text(document)
```

#### 关键原则
- **chunk_size**: 太小丢失上下文，太大检索不准。500-1000 tokens 是经验值
- **chunk_overlap**: 10-20% 重叠避免关键信息刚好在边界被切断
- **保持语义完整**: 不要在句子中间切断

### Step 2: 向量化 (Embedding)

把文本转成数字向量，语义相近的文本向量也相近。

```
"今天天气真好" → [0.12, -0.34, 0.78, ..., 0.05]  (1536维向量)
"今天气候不错" → [0.11, -0.32, 0.75, ..., 0.04]  (向量很接近)
"数据库连接失败" → [0.89, 0.21, -0.45, ..., -0.67]  (向量差很远)
```

#### 常用 Embedding 模型

| 模型 | 维度 | 特点 |
|------|------|------|
| OpenAI text-embedding-3-small | 1536 | 性价比高，最常用 |
| OpenAI text-embedding-3-large | 3072 | 精度最高 |
| BGE-M3 (BAAI) | 1024 | 开源、支持中英文、多语言 |
| Cohere Embed v3 | 1024 | 企业级，支持多语言 |
| Jina Embeddings v2 | 768 | 开源，支持 8K 长文本 |

```python
# Embedding 示例
import openai

response = openai.embeddings.create(
    model="text-embedding-3-small",
    input="这个项目的 CI/CD 怎么配置？"
)
vector = response.data[0].embedding  # [0.123, -0.456, ...] 1536维
```

### Step 3: 检索 (Retrieval)

从向量数据库中找和问题向量最相似的文档段。

#### 相似度计算

```
余弦相似度 (Cosine Similarity): 最常用
  = (A·B) / (|A| × |B|)
  值域 [-1, 1]，越接近 1 越相似
```

#### 检索策略

| 策略 | 说明 |
|------|------|
| **Top-K** | 返回最相似的 K 个结果（K=3~10） |
| **相似度阈值** | 只返回相似度 > 0.7 的结果 |
| **MMR (最大边际相关)** | 平衡相似度和多样性 |
| **Hybrid Search** | 关键词搜索 + 向量搜索混合 |

#### 重排序 (Reranking)

初检索返回 Top-20，再用更强的模型重新排序取 Top-3：

```python
# Reranker 示例（Cohere）
results = cohere.rerank(
    query="CI/CD 配置",
    documents=initial_results,  # 初检索的 20 个结果
    top_n=3                     # 返回最相关的 3 个
)
```

### Step 4: 生成 (Generation)

把检索到的文档 + 用户问题组合成 Prompt，发给模型生成回答。

```python
prompt = f"""基于以下文档回答问题。如果文档中没有相关信息，请明确说明。

文档：
{retrieved_docs}

问题：
{user_question}

回答："""

response = model.chat(prompt)
```

## 三、RAG 高级策略

### 3.1 查询重写

用户的问题可能很模糊，先让模型改写为更适合检索的形式：

```
用户原问题: "那个蓝色的按钮怎么改"
查询重写后: "如何修改前端蓝色按钮的样式和功能"
```

### 3.2 父子文档

文档切两层：
- **父文档**: 大段（2000 tokens），保留完整上下文
- **子文档**: 小段（500 tokens），用于检索匹配

检索时用子文档，生成时返回对应的父文档。

### 3.3 多跳检索

复杂问题需要多步检索：

```
问题: "张三写的那个模块用了什么数据库？"

第1跳: 检索"张三 模块" → 找到"用户管理模块"
第2跳: 检索"用户管理模块 数据库" → 找到"PostgreSQL + Redis"
```

### 3.4 GraphRAG

不是检索文本段落，而是检索知识图谱中的实体关系：

```
传统 RAG: "张三" → 包含"张三"的文档段落
GraphRAG: "张三" → [实体] → (工作于)→ [部门:前端] → (负责)→ [模块:用户管理]
```

## 四、常见 RAG 架构

### 最简单

```
文档目录 → Chunking → Embedding → 存向量DB
用户问题 → Embedding → 检索 → 拼接 → 模型回答
```

### 生产级

```
文档源 (Notion/Confluence/GitHub)
  ↓
Ingestion Pipeline (切分/清洗/向量化)
  ↓
向量数据库 (Chroma/Qdrant) + 关键词索引
  ↓
检索层 (Hybrid Search + Reranker)
  ↓
后处理 (去重/排序/格式化)
  ↓
注入 System Prompt → 模型生成
```

## 五、RAG 评估指标

| 指标 | 含义 | 评估方法 |
|------|------|---------|
| **命中率** | 检索结果中是否包含正确答案 | 人工标注 |
| **MRR** | 正确答案在检索结果中的平均排名 | 自动化 |
| ** faithfulness** | 回答是否基于检索文档（不是编的） | LLM-as-Judge |
| ** relevancy** | 检索结果和问题是否相关 | LLM-as-Judge |

常用评估工具：**Ragas** (开源 RAG 评估框架)

## 六、学习建议

1. **先跑通最简单流程**: 10 行 Python 就能实现基础 RAG
2. **用 Chroma 起步**: 嵌入式向量 DB，不需要额外部署服务
3. **理解 Chunk 策略**: 这是 RAG 效果的最关键变量
4. **加 Reranker**: 这是性价比最高的优化（检索 20 取 3，重排序）
5. **评估优先**: 没有评估，你不知道改了 Chunk 策略是变好还是变坏
