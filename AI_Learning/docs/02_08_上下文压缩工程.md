# 02_08 — 上下文压缩工程实践

> Agent 最大的工程挑战不是模型不够聪明，而是对话太长装不下。

---

## 一、问题：上下文是稀缺资源

```
Claude Sonnet 4.6 上下文窗口: 200K tokens
一次典型 Agent 交互:
  System Prompt:      ~10K tokens   (5%)
  工具说明:           ~15K tokens   (7.5%)
  CLAUDE.md:          ~5K tokens    (2.5%)
  MEMORY.md:          ~3K tokens    (1.5%)
  ————————————————————————————————
  剩余可用:           ~167K tokens  (83.5%)

每个 turn 消耗:
  用户输入:           ~0.5K tokens
  代码上下文:         ~5K tokens
  模型输出:           ~2K tokens
  工具结果:           ~3K tokens
  ————————————————————————————————
  每轮约:             ~10K tokens

理论最大轮次: 167K / 10K ≈ 16 轮
实际有效轮次: ~10 轮 (留 buffer 给模型输出)
```

10 轮对于复杂任务（大型重构、多文件操作）完全不够用 → **必须压缩**。

## 二、四层压缩策略

### 策略总览

```
每轮 Agent 循环按优先级检查:

Layer 1: Snip          ← 最快、零成本
  ↓ 不够
Layer 2: Microcompact  ← 缓存编辑，清除冗余
  ↓ 还不够
Layer 3: Context Collapse ← 折叠对话段落
  ↓ 还不够
Layer 4: Autocompact   ← 完整压缩 + 摘要（最重）
```

### Layer 1: Snip — 裁剪过期数据

```
原理: 删除最旧的消息（保留最近 N 条）

示例:
  对话 100 条消息 → 保留最近 30 条 → 删除前 70 条

适用:
  ✅ 旧工具结果已经没用了
  ✅ 早轮次的探索/试错已不再需要
  ❌ 关键决策发生在早期消息中

实现要点:
  1. 标记哪些消息是"可安全删除"的（工具结果 vs 决策消息）
  2. 保留最近 N 轮（N 根据上下文预算动态调整）
  3. 删除的消息不永久丢失（存在 transcript JSONL 中）
```

### Layer 2: Microcompact — 缓存编辑

```
原理: 清除冗余的 tool results，它们已经被模型消化了

示例:
  工具调用: Read file.ts → 返回 100 行代码
  工具调用: Edit file.ts → 返回 "修改成功"
  工具调用: Read file.ts → 返回修改后的 102 行代码（内容和第一次重复 95%）

Microcompact 后:
  保留第一次 Read（完整上下文）
  删除中间 Edit 的 result（已经体现在后续对话中）
  保留最后一次 Read（当前状态）
```

### Layer 3: Context Collapse — 对话段落折叠

```
原理: 把多轮对话"压缩"成一个摘要

原来:
  User: 帮我加一个登录页面
  Agent: 好的，我先看下项目结构 → [Read 20个文件]
  Agent: 我了解了，开始创建 → [Write LoginForm.tsx]
  Agent: 有点问题，样式不对 → [Edit LoginForm.tsx]
  Agent: 现在好了，测试通过 → [Bash npm test]
  (5 轮，15K tokens)

折叠后:
  [已折叠: 创建登录页面 LoginForm.tsx，经过 2 次修改后测试通过。]
  (1 条系统消息，200 tokens)

节省: 15K → 200 tokens (98.7% 压缩率)
```

### Layer 4: Autocompact — 完整压缩

```
原理: 让模型自己生成压缩摘要

流程:
  1. 检测上下文接近上限 (如 >70%)
  2. 调用模型（用一个小/便宜的模型）生成摘要
  3. 摘要包含: 做了什么、当前状态、遗留问题
  4. 用摘要 + 最近几条消息替换整个对话历史
  5. 继续 Agent 循环

优点: 最彻底
缺点: 有成本（调一次模型）、可能丢失细节
```

## 三、压缩时机决策

```typescript
function shouldCompact(messages: Message[], model: string): boolean {
  const usage = tokenCount(messages)
  const window = getContextWindow(model)
  const ratio = usage / window

  if (ratio > 0.85) return true   // 紧急：必须压缩
  if (ratio > 0.70) return true   // 预警：建议压缩
  if (ratio > 0.50 && messages.length > 50) return true  // 消息太多

  return false
}
```

### 压缩预算分配

```
总上下文 200K:
  System Prompt:     始终保留 (10K, 5%)
  当前轮消息:        始终保留 (10K, 5%)
  最近 3 轮:          始终保留 (30K, 15%)
  中间轮次:           压缩为摘要 (10K, 5%)
  早期轮次:           裁剪/Nip (释放 140K, 70% → 可继续 14 轮)
```

## 四、压缩质量评估

```
好压缩:
  ✅ 保留了关键决策和上下文
  ✅ 后续 Agent 行为没有退化
  ✅ 没有引入幻觉（编造不存在的操作）

坏压缩:
  ❌ 丢失了关键信息 → Agent 后续行为出错
  ❌ 摘要太长 → 没省多少 token
  ❌ 摘要有误 → Agent 基于错误信息做决策

评估:
  1. 压缩前后 Agent 在同样任务上的表现差异
  2. 压缩率 (压缩后 token / 压缩前 token)
  3. 信息保留率 (人工/LLM-as-Judge 评分)
```

## 六、工程实践建议

```
1. 先实现最简单的 Snip → 80% 的问题都是旧消息太多
2. 再实现 Autocompact → 处理真正长的任务
3. 按需加 Microcompact 和 Collapse → 精细化优化
4. 监控压缩频率 → 太频繁说明 Agent 做太多无用功
5. 用户可感知 → /compact 命令让用户手动触发
6. 压缩不可逆 → 提供"查看完整历史"途径
```
